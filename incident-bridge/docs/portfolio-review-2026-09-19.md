# 제출 전 검토와 아키텍처 제안

검토일: 2026-09-19. 사용자가 전달한 공고 기준 신청 마감은 2026-09-22 23:59다. 별도 시간대 표기는 없으며 국내 행사 맥락상 한국 시간으로 계획한다. 제출 형식·포트폴리오 분량·링크 첨부 방식은 미확인이다.

검토 대상은 Claude 세션 `bbf96e16-9714-4676-88e0-605bd3b42ef3`와 현재 로컬 저장소다. 이 문서는 설계 제안이며 아래 개선 기능을 구현했다는 뜻이 아니다. 이번 검토에서는 애플리케이션·인프라 코드를 변경하거나 AWS 리소스를 생성하지 않았다.

## 판단

문제의식과 구성 요소는 괜찮지만, 현재는 통합 운영 시스템보다 여러 실험을 연결하려는 프로토타입에 가깝다. 실행 증거뿐 아니라 실제 배포 경로, 지표의 의미, 회복 판정의 신뢰성을 수정해야 한다. 따라서 Claude의 “새 기능보다 검증 우선”에는 동의하지만 “이미 있는 것을 실행하기만 하면 된다”는 결론에는 동의하지 않는다.

제출용 주제의 추천 초안:

> Incident Bridge는 클라우드 운영 지표·사용자 신고·배포 이력을 연결해 AI가 근거를 붙인 원인 후보와 확인 절차를 제안하고, 실제 사용자 동작의 회복을 검증한 뒤 장애를 종료하는 운영 도구다. 대표 실험은 HTTP 200과 readiness가 정상이어도 LLM 답변이 실패하는 상황이다.

이 문장은 향후 실험 완료 후 사용할 목표 문구다. 지금 제출한다면 ‘이 흐름을 설계하고 일부 구현했다’고 범위를 낮춰야 한다.

## 전달받은 공고에 맞춘 우선순위

공고 주제는 ‘클라우드와 AI를 최대한 활용한 차세대 클라우드 관리 시스템 구축’이며 상세 주제는 킥오프에서 발표된다. 공고상 평가 항목은 실제 동작하는 데모, 팀워크, 독창성, 클라우드 활용도, AI 활용도다. 이 기준이 참가 신청 심사에도 동일한 가중치로 쓰인다는 근거는 전달된 내용에 없다.

| 공고 항목 | 현재 프로젝트가 보여줄 수 있는 것 | 보완할 증거 |
|---|---|---|
| 실제 작동하는 데모 | 테스트용 incident 흐름과 구성 요소 | 한 장애의 관측·조치·회복을 끝까지 실행한 타임라인 |
| 클라우드 활용도 | Terraform, AWS EC2/ECR/SSM, OIDC 설계 | 실제 배포 실행, 동일 SHA 확인, 제한된 권한으로 수행한 복구 |
| AI 활용도 | 감시 대상 채팅 앱의 LLM 호출, triage webhook 확장점 | 운영 증거를 해석하는 실제 AI 호출과 근거 정확성 평가 |
| 독창성 | 고객 신고와 지표 연결, ADR 위반/전제 재검토 구분 | 스트리밍의 숨은 실패를 밝혀내고 잘못된 해결 판정을 막는 사례 |
| 팀워크 | 분리된 모듈과 runbook 초안 | 다른 사람이 재현 가능한 절차, 역할별 입력/출력 계약, 실제 피드백이 있다면 기록 |

이번 제출물은 참가 신청용 포트폴리오다. 해커톤 본 작업과 동일한 결과물이라고 전제하거나 상세 주제를 미리 확정하지 않는다. 혼자 만든 프로젝트로 팀 협업 성과를 주장하지 않으며, 협업 가능한 인수인계 품질을 보여준다.

클라우드 구축 경험을 보여줄 수 있다는 점은 채용 포지션과 관련 있지만, 이 프로젝트 하나로 채용 조건 충족이나 합격을 보장할 수는 없다.

## Claude 세션 검토

잘한 점:

- ADR의 선택 이유·포기한 점·재검토 조건을 보존했다.
- incident 병합 시간 제한, 중복 입력, 상태 전이, 배포 후 확인 연결의 부재를 지적했다.
- DB 초기화 전에 비밀번호를 준비해야 한다는 문제와 shell tracing 유출 위험을 짚었다.
- 실제 실행 결과를 포트폴리오 증거로 남기자는 방향이 타당하다.

수정해야 할 판단:

- `ignore_changes = [value]`는 값의 덮어쓰기를 억제하는 설정이지 state 저장을 차단하는 기능이 아니다. 현재 ADR-010 수정 완료 판단은 잘못됐다.
- `.tfstate`, 로컬 DB, 실행 캡처의 부재는 로컬에서 실행 증거를 찾지 못했다는 뜻이다. 다른 환경·원격 backend에서 한 번도 실행하지 않았다는 증거는 아니다.
- 커밋 2개만으로 작업의 진정성이나 지원 적합성을 단정할 수 없다. 앞으로 실제 작업 단위로 기록하되, 커밋 개수 늘리기를 목표로 하지 않는다.
- `ESCALATED`가 반드시 종료 상태라는 전제는 없다. 사람에게 담당을 넘긴 진행 상태로 둘 수 있다. 문제는 상태 의미와 병합 정책이 불명확하다는 것이다.
- SQLite를 쓴다고 현재 규모에서 반드시 lock 오류가 나는 것은 아니다. 우선 단일 프로세스, 짧은 트랜잭션, 중복 방지·갱신 일관성을 검증한다.
- SLO burn-rate와 baseline 대비 상대적 지연 탐지는 같은 기능이 아니다. 무엇을 성공으로 정의했는지가 먼저다.
- 요청 미들웨어의 duration만 histogram으로 옮겨도 SSE 완료 시간은 측정되지 않는다. 스트림 내부와 외부 사용자 경로를 계측해야 한다.

추가 배포 검증 사항:

- CI와 배포는 독립 workflow다. 테스트 통과한 동일 SHA만 배포하도록 연결해야 한다.
- `ssm_prefix` 문자열만 전달하므로 새 bootstrap이 요구하는 SSM 파라미터와 IAM 정책 준비 순서를 Terraform이 자동으로 전부 보장하지 않는다. 명시적 의존성과 제한된 재시도·준비 확인이 필요하다.
- 현재 배포 스크립트의 `echo "...=$(ssm_get ...)"`는 내부 조회 실패가 echo 성공으로 가려질 수 있다. 시크릿 조회·검증 완료 후 환경 파일을 원자적으로 교체하는 설계가 필요하다.
- `docker compose up` 자체가 실패하면 `set -e`로 readiness 뒤의 rollback 구문까지 도달하지 않을 수 있다. 실패 단계별 처리와 rollback 이후 재검증을 확인한다.
- `user_data_replace_on_change`는 인스턴스를 교체한다. 루트 볼륨의 DB 데이터 보존·복구 여부를 별도 문제로 다뤄야 한다.
- 이미지 rollback은 DB 비밀번호 불일치나 데이터 손상을 복구하지 못한다. 기존 데이터가 있다면 삭제 대신 일관성 복구 절차를 먼저 설계한다.

## ADR-010의 수정 방향

확인한 AWS provider v5.40.0 소스는 SSM GetParameter를 `WithDecryption: true`로 호출한 뒤 `d.Set("value", param.Value)`를 수행한다. 선언된 `~> 5.40` 범위에서 확인한 구체적 버전이며 현재 설치된 정확한 provider 버전은 확인하지 못했다. 일반 value 필드를 쓰는 현재 패턴에 “state에 비밀이 절대 없다”는 주장을 붙이면 안 된다.

제출 기한 내 추천은 Terraform과 비밀 값의 소유권을 명확히 분리하는 것이다.

- Terraform: 네트워크·인스턴스·IAM·비밀 경로 규약을 관리한다.
- 별도 초기화 절차: SSM 비밀 파라미터의 생성과 값을 관리한다. DB 값은 최초 1회 생성하고 재실행 시 재사용한다.
- 런타임: 필요한 이름의 파라미터만 읽는다. 배포 전에 미설정·플레이스홀더·조회 실패를 검사한다.
- 쓰기 권한은 가능하면 초기화 주체에만 둔다. EC2 bootstrap을 택한다면 제한된 쓰기 권한이 계속 남는 대가를 문서화한다.
- 읽고 나서 overwrite하는 방식은 동시 실행에 안전하지 않다. 초기화 실행을 직렬화하거나 생성 전용 충돌 처리 후 저장된 승자 값을 재조회한다.
- 이미 Terraform이 관리하는 실리소스가 있다면 단순 resource 삭제는 파라미터 파괴 계획을 만들 수 있다. 현재 state·리소스 존재를 확인하고 비파괴 소유권 이전을 계획한다.

다른 선택지는 write-only/ephemeral 기능의 지원 버전을 고정해 검증하는 것이다. 다만 이는 버전·provider 동작을 추가 검증해야 하므로 이번 마감의 기본안으로 삼지 않는다. 과거 state에 이미 비밀이 들어갔다면 향후 경로 수정만으로 과거 이력에서 사라지지는 않는다.

검증은 실제 비밀 대신 비밀이 아닌 테스트 표식을 사용한 격리 실험으로 한다. 계획·state에서 그 표식이 어떻게 이동하는지 관찰하고, 제출 자료에는 값·state 원문을 포함하지 않는다. 이번 검토에서는 AWS state를 읽거나 이 실험을 실행하지 않았다.

## 차별성 평가와 선택

알람 그룹화와 정책 검사는 이미 기존 도구가 다룬다. incident.io는 시간·속성 기반 그룹화를 제공하고 Conftest는 Terraform 등을 대상으로 정책 테스트를 제공한다. 따라서 “알람을 묶었다”, “정책을 코드로 만들었다”만으로 독창성을 주장하기는 어렵다.

| 방향 | 강점 | 22일까지의 판단 |
|---|---|---|
| 범용 AI 자동 장애 복구 플랫폼 | 넓은 활용 가능성 | 자동 수정 안전성·원인 분석·외부 연동까지 범위가 너무 넓다. 후순위. |
| ADR 위반과 전제 재검토를 구분하는 도구 | 인프라 판단 과정을 설명하기 좋음 | 보조 사례로 유지. 자료 수집과 판정의 한계를 명시한다. |
| LLM 스트리밍의 숨은 실패와 회복 검증 | 현재 앱의 실제 실패 경로와 직접 연결됨 | 대표 데모로 추천. 하나의 장애를 끝까지 재현할 수 있다. |

차별점은 개별 기술의 최초 발명보다 다음의 연결을 직접 증명하는 데 둔다: 사용자 증상 → 실제 요청/스트림 증거 → 조치 → 같은 증상의 회복 → 모니터링 또는 ADR 개선.

## 추천 아키텍처 — 제안, 미구현

```text
채팅 앱 + 통제 가능한 LLM 테스트 upstream
              │
              ├─ 스트림 결과 이벤트 ─┐
외부 synthetic client ─ 측정 이벤트 ─┼─ 정규화·중복 제거 → 증거 저장소
고객 문의 / request_id ──────────────┘                        │
                                                    incident 연결
                                                           │
                                            사람이 원인 확인·복구 실행
                                                           │
                                               동일 경로 재검증
                                                           │
                                          회복 증거 충족 시 RESOLVED

ADR 검사 → 근거 있는 위반 / 전제 재검토 / 증거 부족을 별도 기록
```

구성 원칙:

- 소규모로 유지한다. 새 Kafka·EKS·벡터 DB를 기본 전제로 삼지 않는다.
- 채팅 앱이 멈춰도 관찰 가능한 외부 client에서 검증한다. 제출 데모에서는 개발자 PC가 이 역할을 할 수 있다. 이를 고가용성 모니터링 서비스라고 표현하지 않는다.
- incidentops는 우선 별도 로컬 프로세스와 SQLite로 실행하고 네트워크 노출을 제한한다. 공개 webhook이 필요하면 입력 인증·권한·재전송 검증이 선행돼야 한다.
- GitHub hosted runner에서 로컬 incidentops로 직접 callback할 수 있다고 가정하지 않는다. 초기에는 로컬 coordinator가 인증된 GitHub API로 같은 SHA의 결과 artifact를 조회해 가져오는 구조가 가능하다. 수동 import라면 수동임을 표시한다.
- synthetic client는 공개 URL의 인증된 `/chat/stream` 경로를 통과한다. 실제 provider를 쓰는 smoke check와 통제된 가짜 upstream으로 하는 반복 장애 실험을 구분한다.

### 최소 데이터 계약

증거마다 다음을 기록한다: event_id, source, environment, service, occurred_at, received_at, request_id, deployment_sha, signal 종류, 측정값, sample_count, window_start/end, collector 버전, 실제/합성 데이터 구분.

모든 필드를 즉시 구현할 필요는 없다. 첫 데모 필수 항목은 중복 식별자·출처·대상·시각·배포 버전·측정 의미·결과다. 누락된 값은 만들어 채우지 않고 unknown으로 남긴다.

- tenant는 감시 대상 앱의 인증 정보에 근거해야 한다. 현재 collector의 임의 tenant 문자열은 실제 멀티테넌트 격리를 증명하지 않는다. 첫 데모는 단일 tenant로 명시해도 된다.
- request_id는 로그·이벤트 연결에 사용한다. Prometheus label로 무제한 사용자 ID·request_id를 넣지 않는다.
- 장애 연결의 기본 범위는 environment + service + endpoint + symptom + 시간 구간이다. 요청 ID가 일치하면 우선 연결하고 애매하면 관련 후보로만 제시한다.
- 중복 제거는 source + event_id 기준으로 한다. 고객의 반복 요청과 동일 이벤트의 재전송을 구분한다.
- SHA가 존재한다는 이유만으로 배포 원인이라고 판단하지 않는다. 현재 triage는 SHA가 있으면 CODE_REGRESSION을 우선 선택하므로 원인과 단순 문맥을 구분해야 한다.

### 스트리밍 성공 정의

현재 `app/routers/chat.py`는 첫 상태 이벤트를 보낸 후 upstream 오류를 스트림 내부 error 이벤트로 전달한다. 따라서 HTTP 5xx 비율과 `/ready`만으로는 이 실패를 볼 수 없다.

- 시작: 사용자 요청이 시작된 시각.
- 첫 응답: `history_loaded` 같은 상태 이벤트가 아니라 첫 비어 있지 않은 답변 content가 도착한 시각. 제출용 표현은 ‘첫 답변 조각 지연’이 정확하다.
- 성공: content 수신과 유효한 upstream 정상 완료를 확인하고, client에서도 정상 완료를 관찰한 경우.
- 실패: upstream 오류, 첫 답변 제한 시간 초과, 청크 사이 제한 시간 초과, 정상 종료 표시 없는 조기 EOF 등을 구분한다.
- 사용자 취소: 장애 실패와 별도 분류하고 포함/제외 정책을 명시한다.
- 현재 upstream reader의 반복문이 종료됐다는 사실만으로 정상 완료를 보장할 수 없으므로 종료 이유를 보존해야 한다.
- p95는 충분한 표본과 명시한 구간에서만 계산한다. 저표본 데모는 성공 건수/시도 건수와 개별 지연을 우선 제시한다. baseline과 임계치는 측정 조건과 함께 기록한다.

### 회복 판정과 상태

주 흐름은 OPEN → TRIAGED → MITIGATING → VERIFYING → RESOLVED로 단순화할 수 있다. 코드 변경을 필요로 하지 않는 upstream 복구·설정 복원도 허용한다.

- ESCALATED는 사람에게 담당을 넘긴 상태로 정의하고 RESOLVED와 구별한다. 상태를 하나 더 늘리기보다 담당자/에스컬레이션 표식을 분리할 수도 있다.
- 해결 전에 ‘원래 증상’과 ‘검증할 경로’를 고정한다. readiness 장애와 스트림 오류를 같은 성공 기준으로 닫지 않는다.
- 배포를 했다면 검증 증거가 조치 이후 생성됐고 대상 environment·실행 중 SHA가 일치해야 한다. rollback이면 실패한 SHA 대신 복구된 SHA를 기록한다.
- 코드 수정에는 해당 SHA의 CI 근거를 요구한다. 무배포 복구에는 CI/deploy를 사실과 다르게 true로 채우지 않고 적용 없음과 이유를 기록한다.
- 첫 데모용 예시는 일정 관찰 구간에서 같은 사용자 동작 5회 연속 성공이다. 이것은 재현 실험의 완료 조건이며 운영 SLO·통계적 신뢰 보장은 아니다.
- 검증 데이터 없음·수집 실패·오래된 증거는 해결 성공으로 바꾸지 않는다. VERIFYING을 유지하고 기한 초과 시 담당자 확인으로 넘긴다.
- 재발하면 이전 incident와 연결한 새 incident를 만들거나 재개 규칙을 명시한다. 기존 회복 증거는 덮어쓰지 않는다.

### ADR 판정

- VALID: 명시된 범위·유효한 수집 시각·완전한 증거 안에서 검사가 통과했다는 뜻.
- VIOLATED: 수용한 규칙에 대한 직접 위반 증거가 있음.
- REVISIT_REQUIRED: 기존 선택의 전제를 검토할 근거가 있음. 단발성 load 상승만으로 EKS 도입 같은 결론을 내리지 않음.
- UNKNOWN: 수집 실패, 오래된 자료, 지원하지 않는 패턴 또는 불충분한 증거.

CI에서는 필수로 지정된 정적 검사만 게이트로 삼는다. VIOLATED와 필수 증거 수집 실패는 실패, REVISIT_REQUIRED는 검토 과제, 로컬 repo 검사 범위 밖 AWS 자료는 검사 대상에서 제외한다. CLI 종료 코드와 구조화된 결과를 함께 정의한다.

### AI의 역할 — 공고 수신 후 추가한 제안

감시 대상 채팅 앱이 LLM을 호출한다는 사실만으로 ‘AI 클라우드 관리’를 입증했다고 설명하지 않는다. 기존 `IncidentTriage`의 webhook 경계를 이용해 운영 분석에서 한 가지 AI 기능을 실제로 검증하는 것이 좋다.

- 입력: 필요한 최소한의 정규화된 증거, 배포 타임라인, 관련 ADR·runbook 일부. 고객 개인정보·비밀 값은 제거한다.
- 출력: 원인 후보 최대 3개, 후보별 evidence_id, 부족한 증거, 가설을 구분할 다음 읽기 전용 확인 항목, 사람이 검토할 조치 제안.
- 사실/가설 구분: ‘현재 SHA가 A다’는 사실이고 ‘A가 원인이다’는 별도 가설이다. 수치형 확률을 근거 없이 정밀하게 제시하지 않는다.
- 수신 검증: 출력 스키마와 evidence_id 존재를 확인한다. 존재하는 ID 인용만으로 내용이 뒷받침되는 것은 아니므로 소규모 사례에서는 사람이 근거 적합성을 평가한다.
- 권한: AI는 장애 종료·AWS 변경·비밀번호 변경을 직접 수행하지 않는다. 사용자 문의와 로그는 분석 자료이며 도구 실행 지시로 신뢰하지 않는다.
- 실패 처리: 모델 timeout/형식 오류/근거 부족이면 규칙 기반 요약과 UNKNOWN으로 전환한다. 모델 호출 실패가 수집과 기록을 막지 않게 한다.
- 평가: 같은 사례를 규칙 기반과 AI 보조로 비교한다. 올바른 가설, 근거 없는 주장, 증거 부족 시 판단 보류, 분석 지연·호출 비용을 기록한다. 모델이 낫지 않은 사례도 남긴다.

최소 평가 사례는 정상, upstream 오류, 첫 답변 지연, DB 연결 실패, 증거 누락 등 5종으로 시작한다. 이는 소규모 기능 점검이며 일반적 정확도나 MTTR 개선을 입증하는 통계로 표현하지 않는다. API 응답을 재생하는 오프라인 데모를 준비한다면 녹화/저장 응답임을 표시하고 실제 호출과 구분한다.

기한이 부족하면 증거 수집·회복 검증을 먼저 완성하고 AI는 작은 triage 하나만 연결한다. 여러 에이전트의 자동 복구 루프를 추가하지 않는다.

## 대표 실험과 제출 증거

| 실험 | 기대하는 관찰 | 완료 기준 |
|---|---|---|
| 정상 기준선 | 같은 사용자 경로가 정상 완료됨 | 시도 수·조건·버전 기록 |
| upstream 오류/지연 | HTTP 200·ready 정상이어도 스트림 실패 또는 첫 답변 지연 발생 | 기존 probe와 새 사용자 경로 검사 차이를 실제 기록 |

추가 방어 검증은 동일 이벤트 재전송, 다른 endpoint의 동시 장애, 오래된 성공 증거, collector 중단 중 네 가지가 우선이다. 실패율·탐지 시간·회복 시간은 실제 반복 실험 결과만 적고 개선 비율을 미리 약속하지 않는다.

3. 대표 장애와 스트리밍 성공·회복 판정 기준, AI triage 입출력 계약을 사용자와 결정한다.
4. 구현 요청이 오면 한 경로씩 작업하고 실제 증거를 수집한다. 대규모 기능 확장으로 돌아가지 않는다.

사용률 95% 자동 감지·현재 대화의 모델/effort 전환은 제공된 도구로 수행할 수 없었다. 공식 안내상 사용 한도는 usage dashboard, CLI에서는 `/status`에서 확인한다. 사용자가 전환할 때 문서 정리·인계만은 작은 모델과 낮은 effort로 이어갈 수 있다. 보안·상태 전이 판단은 근거를 보존해 별도 검토한다.
