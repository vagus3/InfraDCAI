# DESIGN.md

무엇이 참이어야 하는가를 정한 문서다. `docs/architecture.md`가 지금 무엇이 있는지를 서술한다면,
여기는 코드가 지켜야 할 규약을 적는다.

이 문서가 없으면 코드가 조용히 어긋나도 아무도 모른다. 실제로 그랬다. `http_probe`가 단일 요청
응답 시간을 `p95_latency` 필드에 넣고 있었는데, 위반할 규약이 없으니 아무 일도 일어나지 않았다.

각 항목에 현재 구현 상태를 표시한다. 정해졌지만 아직 구현하지 않은 것을 구현된 것처럼 쓰지 않는다.

## 1. 성공의 정의 — 스트리밍 응답

상태: 정의됨, 미구현

이 프로젝트의 대표 실패는 "HTTP는 200인데 사용자는 답을 못 받는 상황"이다. `app/routers/chat.py`가
upstream 오류를 스트림 안의 error 이벤트로 보내기 때문에, 상태 코드와 `/ready`만으로는 보이지 않는다.

그래서 성공을 상태 코드가 아니라 사용자가 받은 것으로 정의한다.

| 시점 | 정의 |
|---|---|
| 시작 | 사용자 요청이 서버에 도착한 시각 |
| 첫 응답 | 첫 번째 비어 있지 않은 `content` 조각이 도착한 시각 |
| 완료 | 정상 종료 표시까지 받은 시각 |

`history_loaded` 같은 상태 이벤트는 첫 응답이 아니다. 그건 서버가 일을 시작했다는 뜻이지
사용자가 답을 보기 시작했다는 뜻이 아니다. 지표 이름은 "첫 답변 조각까지의 지연"이라고 쓴다.

성공은 세 가지가 모두 참일 때다.

1. 비어 있지 않은 content를 한 조각 이상 받았다
2. upstream이 정상 완료로 끝났다
3. 클라이언트에서도 정상 종료를 관찰했다

실패는 하나로 뭉뚱그리지 않고 구분한다.

- upstream 오류 (모델이 거부, 인증 실패, rate limit)
- 첫 조각 시간 초과
- 조각 사이 시간 초과
- 정상 종료 표시 없는 조기 EOF

사용자 취소는 실패가 아니다. 별도로 분류하고, 집계에 포함할지 여부를 명시한다.

주의: upstream reader의 반복문이 끝났다는 사실만으로 정상 완료를 보장할 수 없다. 종료 이유를
보존해야 한다. 현재 upstream reader는 종료 표식 없는 EOF를 `UpstreamIncompleteError`로
구분한다. 첫 content 시각·클라이언트 완료 관찰·성공률 계측까지 구현된 것은 아니다.

## 2. 증거(evidence)의 최소 규약

상태: 정의됨, 미구현

모든 관측 기록은 아래를 갖는다. 모르는 값은 만들어 채우지 않고 `unknown`으로 남긴다.

| 필드 | 이유 |
|---|---|
| `event_id` | 같은 이벤트의 재전송을 구분하기 위해 |
| `source` | 누가 보냈는지. 중복 제거의 한 축 |
| `environment` / `service` / `endpoint` | 어디서 났는지 |
| `occurred_at` / `received_at` | 두 시각이 다르면 수집 지연이 있다는 뜻 |
| `request_id` | 로그와 이벤트를 잇는 열쇠 |
| `deployment_sha` | 어느 버전에서 났는지 |
| 측정 의미 | 무엇을 잰 값인지. `p95`인지 단일 표본인지 |
| `sample_count` / `window` | 백분위수를 백분위수라고 부를 수 있는 근거 |
| 실제/합성 구분 | 합성 트래픽으로 만든 값을 실사용 지표로 섞지 않기 위해 |

규칙 두 개를 덧붙인다.

- 백분위수는 표본 수와 구간을 함께 기록할 때만 백분위수라고 부른다. 표본이 적으면
  "성공 건수 / 시도 건수"와 개별 지연을 먼저 제시한다.
- `tenant`는 감시 대상 앱의 인증 정보에 근거해야 한다. collector가 임의로 붙인 문자열은
  멀티테넌트 격리를 증명하지 않는다. 첫 데모는 단일 tenant라고 명시한다.

## 3. incident 연결 규칙

상태: 정의됨, 현재 구현과 불일치

연결 범위는 `environment` + `service` + `endpoint` + `symptom` + 시간 구간이다.

- `request_id`가 일치하면 우선 연결한다
- 애매하면 자동으로 합치지 않고 관련 후보로만 제시한다
- 중복 제거는 `source` + `event_id` 기준이다. 고객이 같은 내용을 두 번 문의한 것과
  같은 이벤트가 두 번 전달된 것은 다르다
- 시간 구간 밖의 열린 incident에는 붙이지 않는다

현재 구현은 UTC 정규화, 시간 창이 있는 최신 미해결 incident 조회, message_id가 있는 고객
문의의 재전송 제거까지 반영했다. 같은 시간 창의 endpoint/symptom 분리와 전체 이벤트의
원자적 처리까지 구현하지는 않았다. 기존 SQLite에는 중복 처리용 nullable 컬럼을 추가하며
과거 기록의 message_id를 자동 복원하지는 않는다.

배포 SHA가 존재한다는 사실만으로 그 배포가 원인이라고 판단하지 않는다. 현재 `triage.py`는
SHA가 있으면 `CODE_REGRESSION`을 먼저 고르되 낮은 신뢰도의 상관 가설이라고 표시한다.
원인과 단순 정황은 구분해야 한다.

## 4. 상태와 회복 판정

상태: 정의됨, 현재 구현과 불일치

```
OPEN → TRIAGED → MITIGATING → VERIFYING → RESOLVED
```

- `ESCALATED`는 종료가 아니라 담당을 사람에게 넘긴 상태다. `RESOLVED`와 구별하고,
  열린 incident 조회에서 제외하지 않는다
- 코드 변경 없는 복구(upstream 회복, 설정 복원)도 정상 경로로 인정한다

해결 판정은 아래를 모두 만족할 때만 한다.

1. 조치 전에 "원래 증상"과 "검증할 경로"를 고정해 두었다
2. 검증 증거가 조치 이후에 생성되었다
3. 검증 대상 environment와 실행 중인 SHA가 일치한다
4. 같은 사용자 동작이 정해진 관찰 구간에서 연속 성공했다

4번의 첫 데모 기준은 5회 연속 성공이다. 이건 재현 실험의 완료 조건이지 운영 SLO가 아니다.
둘을 같은 숫자로 쓰지 않는다.

지키는 것들:

- readiness 장애와 스트림 오류를 같은 성공 기준으로 닫지 않는다
- 코드 수정에는 해당 SHA의 CI 근거를 요구한다. 무배포 복구에는 CI/deploy를 사실과 다르게
  `true`로 채우지 않고 "적용 없음"과 이유를 기록한다
- rollback이면 실패한 SHA가 아니라 복구된 SHA를 기록한다
- 검증 데이터 없음, 수집 실패, 오래된 증거는 성공으로 바꾸지 않는다. `VERIFYING`을 유지하고
  기한을 넘기면 담당자 확인으로 넘긴다
- 재발하면 이전 incident와 연결된 새 incident를 만든다. 기존 회복 증거를 덮어쓰지 않는다

현재 `incidentops/service.py`의 `verify()`는 외부에서 받은 bool 세 개로 종료를 결정한다.
대상 배포와 측정 시각을 확인하지 않는다. API는 운영자 토큰을 확인하지만 그 토큰이 회복의
증거를 대신하지 않는다. 따라서 위 규약과 어긋나는 상태다.

2026-09-22 제출 준비에서 `/api/v1/*` 전체에 공통 운영자 토큰 검사를 적용했다. 토큰 미설정은
503으로 차단하며, 읽기·수집도 예외가 아니다. 이는 단일 운영자 접근 통제이며 tenant별 권한
격리나 공개 서비스 보안 완료를 의미하지 않는다.

## 5. ADR 판정의 의미

상태: 부분 구현. 위반 및 승인 게이트는 구현됐지만, 증거 누락·신선도 판정은 아래 규약과 불일치한다.

| 판정 | 뜻 |
|---|---|
| `VALID` | 명시된 범위 안에서, 유효한 수집 시각에, 완전한 증거로 통과했다 |
| `VIOLATED` | 수용한 규칙에 대한 직접 위반 증거가 있다 |
| `REVISIT_REQUIRED` | 기존 선택의 전제를 검토할 근거가 생겼다 |
| `UNKNOWN` | 수집 실패, 미지원 패턴, 오래된 자료, 증거 부족 |

`VALID`는 "안전하다"가 아니라 "내가 물어본 질문에 대해서는 이상 없다"는 뜻이다. 질문이 틀리면
`VALID`가 오히려 위험하다. ADR-010에서 실제로 그런 일이 있었고, 그 기록은 `DECISIONS.md` 10번에 있다.

증거를 수집하지 못한 경우를 `VALID`로 처리하지 않는다. 현재 `engine.py`의 security group 검사는
스냅샷에 security group이 없으면 빈 목록으로 보고 `VALID`를 낸다. 수집 성공 여부와 검사 통과
여부를 분리해야 하는 자리다.

CI 게이트 정책:

- `VIOLATED`와 필수 증거 수집 실패는 실패로 처리한다
- `REVISIT_REQUIRED`는 검토 과제이지 실패가 아니다
- 로컬 저장소 검사 범위 밖의 AWS 자료는 `repo` 모드 검사 대상에서 제외한다
- 위반에 유효한 승인 기록(`acknowledgement`)이 있으면 크게 출력하되 막지는 않는다

마지막 항목이 핵심이다. 위반을 보고하고 종료 코드 0을 반환하면 체커는 장식이 된다.
반대로 고칠 수 없는 위반에 CI를 영구히 막아두면 사람들은 `|| true`를 붙인다. 승인 기록은
그 둘 사이의 자리다. 누군가 이름과 기한을 걸고 이 상태로 배포하기로 했다는 기록이다.

### 승인 기록의 요건

승인이 CI를 통과시킨다면 승인 자체가 보안 통제다. 그러면 통제에 필요한 성질을 갖춰야 한다.
처음 구현은 "기록이 존재하는가"만 봤고, 그건 날짜를 입은 영구 면제였다.

위험 수용은 유지관리자가 결정한다. 에이전트는 검사를 통과시키기 위해 승인 기록을 스스로 만들거나
기한·지문을 갱신하지 않는다. 명시적으로 승인된 범위만 기록하며, 범위가 달라지면 기존 승인을 재사용하지 않는다.

승인은 아래를 모두 만족할 때만 유효(`active`)하다.

| 필드 | 없거나 틀리면 |
|---|---|
| `accepted_on`, `owner`, `reason` | `malformed` |
| `expires_on` | 없거나 형식 오류면 `malformed`, 지났으면 `expired` |
| `fingerprint` | 현재 findings와 다르면 `stale` |

`active`가 아닌 모든 상태는 CI를 막는다. 읽을 수 없는 통제는 통제가 아니므로 `malformed`도
막는다.

`fingerprint`는 evidence details의 정규화 JSON을 SHA-256으로 줄인 값이다. 승인을 "이 ADR"이
아니라 "사람이 실제로 검토한 그 findings"에 묶기 위한 것이다. 이게 없으면 3개를 승인한 기록이
4번째가 생긴 뒤에도, 그중 하나가 다시 비밀을 생성하기 시작한 뒤에도 계속 체커를 침묵시킨다.

findings의 파일 경로는 저장소 상대 경로여야 한다. 절대 경로는 기기마다 달라서 CI에서 매번
드리프트로 읽힌다.

## 6. AI의 권한 경계

상태: 정의됨, 미구현 (`triage.py`의 webhook 경계가 연결 지점)

부분 반영: triage 요청은 외부 전송용 허용 목록을 사용하며 고객 fact의 원문·이름/제목 요약과
이전 triage 결과를 제외한다. 통신·JSON·응답 스키마 오류는 `UNKNOWN`과 수동 검토로 전환한다.
모든 자유 텍스트의 민감정보 탐지, evidence_id 검증, 모델 평가까지 구현한 것은 아니다.

감시 대상 앱이 LLM을 호출한다는 사실은 "AI로 클라우드를 관리한다"의 근거가 아니다.
운영 분석에서 AI가 실제로 하는 일이 있어야 한다.

입력으로 주는 것:

- 정규화된 증거 (2번 규약을 따르는 것만)
- 배포 타임라인
- 관련 ADR과 runbook의 일부
- 고객 개인정보와 비밀 값은 제거한다

출력으로 요구하는 것:

- 원인 후보 최대 3개
- 후보별 `evidence_id` (존재하는 것만)
- 부족한 증거가 무엇인지
- 가설을 구분할 다음 확인 항목 (읽기 전용)
- 사람이 검토할 조치 제안

지키는 것들:

- 사실과 가설을 구분한다. "현재 SHA가 A다"는 사실이고 "A가 원인이다"는 가설이다
- 근거 없이 정밀한 확률 수치를 제시하지 않는다
- 출력 스키마와 `evidence_id` 존재를 검증한다. 다만 존재하는 ID를 인용했다는 사실이
  내용을 뒷받침하지는 않으므로, 소규모 사례는 사람이 근거 적합성을 평가한다
- AI는 incident 종료, AWS 변경, 비밀번호 변경을 직접 수행하지 않는다
- 고객 문의와 로그는 분석 자료다. 도구 실행 지시로 신뢰하지 않는다
- 모델 timeout, 형식 오류, 근거 부족이면 규칙 기반 요약과 `UNKNOWN`으로 전환한다.
  모델 호출 실패가 증거 수집과 기록을 막지 않는다

평가는 같은 사례를 규칙 기반과 AI 보조로 비교해서 한다. 올바른 가설, 근거 없는 주장,
증거 부족 시 판단 보류, 분석 지연과 호출 비용을 기록한다. 모델이 더 낫지 않았던 사례도 남긴다.
최소 사례는 정상 / upstream 오류 / 첫 답변 지연 / DB 연결 실패 / 증거 누락의 5종이다.

이건 소규모 기능 점검이다. 일반적인 정확도나 MTTR 개선을 입증하는 통계로 표현하지 않는다.
