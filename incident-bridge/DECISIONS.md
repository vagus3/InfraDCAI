# 기술 선택 기록

각 항목은 **무엇을 선택했는가 / 무엇과 비교했는가 / 왜 그렇게 골랐는가 / 언제 이 결정을 뒤집을 것인가**
순서로 적었다. 마지막 항목이 특히 중요하다. "이 기술이 언제 필요해지는지"를 말할 수 있어야
기술을 이해하고 고른 것이고, 아니면 그냥 이름을 아는 것이다.

---

## 1. Kubernetes를 쓰지 않았다

**비교 대상**: EKS / ECS / 단일 EC2 + Docker Compose
**선택**: 단일 EC2 + Docker Compose

이 서비스는 사용자가 나 혼자고, 상태를 가진 컨테이너(Postgres, Redis)가 있고, 무중단 배포가
필요할 만큼의 트래픽이 없다. Kubernetes가 해결하는 문제는 "여러 노드에 걸친 스케줄링, 셀프힐링,
선언적 롤아웃"인데 그 문제가 아직 존재하지 않는다. 없는 문제를 위해 컨트롤 플레인 비용(EKS는
클러스터당 시간당 요금)과 운영 복잡도를 지불하는 셈이 된다.

Compose 파일의 서비스 4개는 각각 Deployment + Service 하나에 거의 1:1로 대응한다. 구조를
이렇게 유지했기 때문에 옮겨야 할 때 옮기는 것은 어렵지 않다.

**이 결정을 뒤집는 시점**: 인스턴스 한 대의 리소스가 부족해져서 앱을 수평 확장해야 할 때,
또는 배포 중 다운타임이 문제가 될 때. 그 시점에는 EKS보다 ECS Fargate를 먼저 검토할 것이다.
관리할 노드가 없고, 필요한 것이 "컨테이너 여러 개를 굴리는 것"뿐이라면 Kubernetes의 표현력이
필요하지 않다.

### 다만 안 써본 채로 내린 결정은 아니다

같은 스택을 로컬 `kind` 클러스터에도 올려봤다. 매니페스트는 `k8s/`에, 무엇을 어떤 순서로
확인했는지는 [K8S-PLAN.md](K8S-PLAN.md)에 있다.

운영 경로에 넣지 않고 학습용으로만 돌린 이유:

- EKS는 컨트롤 플레인만 시간당 과금된다. 배우려고 켜놓을 물건이 아니다.
- kind로도 배우려는 것 — 스케줄링, probe, 롤아웃, Service 디스커버리 — 은 다 확인된다.
  확인이 안 되는 건 멀티 AZ, 클라우드 로드밸런서 연동, 실제 노드 오토스케일링 정도다.

> **아래는 아직 직접 확인하기 전의 초안이다.** K8S-PLAN.md의 세션을 끝내고 나서
> 실제로 관찰한 것으로 다시 쓸 것. 여기 적힌 게 맞는지 틀린지 자기 눈으로 확인하지
> 않았다면, 면접에서 한 단계만 더 파고들어도 바로 막힌다.

확인해봐야 할 것들 (예상):

- **무중단 배포는 K8s가 공짜로 주지 않는 것 같다.** `maxUnavailable: 0`과 제대로 된
  readinessProbe가 맞아야 동작할 것으로 보인다. → Session 5에서 실제로 502가 섞이는지 확인
- **상태 있는 워크로드가 가장 까다로울 것.** Postgres는 StatefulSet이어야 하고 PVC
  생명주기를 따로 이해해야 한다. → Session 3에서 PVC를 지웠을 때 무슨 일이 나는지 확인
- **replica 2개면 앱 시작 시 `create_all()`이 동시에 실행된다.** 컨테이너가 하나일 때는
  없던 문제다. → Session 1에서 실제로 충돌하는지, 아니면 조용히 넘어가는지 확인

세 개 다 확인하고 나면, 위 문장들을 **"~일 것 같다"에서 "~였다"로** 바꿔 쓸 것.
그리고 예상과 달랐던 게 있으면 그게 제일 좋은 이야깃거리다.

지향점은 "필요 없어서 안 썼다"가 아니라 **"양쪽 다 돌려보고, 이 규모에서는 얻는 것보다
드는 게 크다고 판단했다"** 이다. 도입 조건은 위의 "이 결정을 뒤집는 시점"에 적어둔 그대로다.

## 2. Postgres와 Redis를 RDS / ElastiCache 대신 컨테이너로 띄웠다

**비교 대상**: RDS + ElastiCache / 같은 인스턴스의 컨테이너
**선택**: 컨테이너

RDS 최소 인스턴스와 ElastiCache 노드를 합치면 이 프로젝트의 나머지 전체보다 비싸다. 자동 백업,
Multi-AZ 페일오버, 자동 마이너 버전 업그레이드가 그 값을 하는 상황이 아니다. 데이터는
계정 정보뿐이고, 유실되면 다시 가입하면 된다.

**대가로 포기한 것**: 인스턴스가 죽으면 데이터도 같이 간다. EBS 볼륨에 남지만 스냅샷을
따로 잡지 않으면 복구 계획이 없는 것과 같다.

**이 결정을 뒤집는 시점**: 남의 데이터를 저장하는 순간. 그때는 백업 없는 DB를 직접 굴리는
것이 비용 절약이 아니라 부채가 된다.

## 3. 대화 기록은 Redis, 계정은 Postgres

같은 데이터베이스에 다 넣지 않은 이유는 두 데이터의 성격이 다르기 때문이다.

| | 계정 | 대화 기록 |
|---|---|---|
| 유실 시 영향 | 사용자가 계정을 잃음 | 맥락만 사라짐, 다시 대화하면 됨 |
| 접근 패턴 | 로그인할 때 1회 | 모든 턴마다 읽고 씀 |
| 수명 | 영구 | 하루 |
| 선택 | Postgres | Redis (TTL 24시간, 최근 20개만 유지) |

Redis에 `maxmemory 128mb` + `allkeys-lru`를 걸어둔 것도 같은 이유다. 메모리가 차면 오래된
대화부터 버려지는 게 맞고, 그것 때문에 서비스가 멈추면 안 된다.

## 4. 세션 대신 JWT

**비교 대상**: 서버 세션(Redis 저장) / JWT
**선택**: JWT

서버에 세션 저장소를 두지 않으므로 앱 인스턴스가 요청을 처리하는 데 다른 인스턴스의
상태가 필요 없다. 지금은 인스턴스가 하나라 차이가 없지만, 앱을 두 대로 늘리는 일이
"로드밸런서 뒤에 붙이기"로 끝나느냐 "세션 공유 설계부터 다시 하기"가 되느냐가 갈린다.

**대가로 포기한 것**: 발급된 토큰을 만료 전에 무효화할 수 없다. 로그아웃은 클라이언트가
토큰을 버리는 것일 뿐 서버는 여전히 그 토큰을 받아준다. 실제 서비스라면 짧은 access token +
refresh token 구조로 가고, refresh token은 서버에서 폐기 가능하게 관리해야 한다.

## 5. WebSocket 대신 SSE

**비교 대상**: WebSocket / Server-Sent Events
**선택**: SSE

데이터가 서버 → 클라이언트 한 방향으로만 흐른다. WebSocket은 양방향 채널을 위해 프로토콜
업그레이드와 그에 맞는 프록시 설정, 재연결 로직을 요구하는데 여기서는 쓰지 않을 기능이다.
SSE는 그냥 HTTP 응답이라 기존 프록시와 인증 헤더가 그대로 동작한다.

이 선택 때문에 프록시 설정을 두 번 건드려야 했다. nginx는 `proxy_buffering off`,
Caddy는 `flush_interval -1`. 둘 다 없으면 응답 전체를 버퍼에 모았다가 한 번에 내보내서
스트리밍이 스트리밍이 아니게 된다.

## 6. 로컬은 Ollama, 배포 환경은 OpenAI

t3.micro는 램 1GB에 GPU가 없다. 로컬 모델을 돌릴 수 있는 하드웨어가 아니다. 반대로 개발 중에
매 요청마다 API 비용을 내는 것도 낭비다. 그래서 `LLM_PROVIDER` 환경변수 하나로 갈리게 했고,
코드에는 두 구현이 같은 인터페이스로 들어가 있다.

**이 결정을 뒤집는 시점**: GPU 인스턴스를 쓸 수 있게 되면. 그때가 로드맵에 있는 vLLM,
KV Cache, Continuous Batching이 실제로 의미를 갖는 지점이다. 지금 그 주제를 공부해도
검증할 환경이 없다.

## 7. 로컬은 nginx, 배포 환경은 Caddy

의도적으로 다르게 썼다. nginx 설정은 한 번은 직접 써봐야 프록시가 실제로 무엇을 설정하는지
알 수 있다. 반대로 운영 환경에서 인증서 발급과 갱신을 직접 관리하는 것은 얻는 게 없다 —
Caddy는 Let's Encrypt 인증서를 알아서 받고 갱신한다.

도메인은 사지 않았다. `nip.io`가 `13-124-5-6.nip.io` 같은 이름을 해당 IP로 해석해주기
때문에 Let's Encrypt가 인증서를 발급해줄 수 있는 실제 호스트명이 생긴다.

## 8. SSH 대신 SSM Session Manager

보안 그룹에 22번 포트가 없다. 배포도 SSH가 아니라 `ssm send-command`로 실행한다.

- 관리할 키페어가 없다. GitHub Secrets에 개인키를 넣을 일도 없다.
- 인터넷에 열린 SSH 포트가 없으므로 자동화된 스캐너의 로그인 시도 대상이 아니다.
- 접속과 실행 기록이 CloudTrail에 남는다.

## 9. Access Key 대신 GitHub OIDC

GitHub Actions는 단기 OIDC 토큰을 AWS 임시 자격증명으로 교환한다. IAM 사용자의 액세스 키를
GitHub Secrets에 넣는 방식과 비교하면, 유출됐을 때의 차이가 크다. 액세스 키는 만료되지 않고
어디서든 쓸 수 있지만, OIDC 신뢰 정책은 특정 저장소의 특정 브랜치로 조건이 걸려 있다.

```
"token.actions.githubusercontent.com:sub" = "repo:OWNER/REPO:ref:refs/heads/main"
```

이 조건이 없으면 GitHub의 아무 저장소나 이 역할을 가져갈 수 있다.

## 10. 시크릿은 Terraform state에 넣지 않았다

Terraform은 SSM 파라미터를 **생성**하지만 실제 값은 모른다. 플레이스홀더로 만들고
`ignore_changes = [value]`를 걸어둔 뒤, 진짜 값은 AWS CLI로 한 번 넣는다.

이유는 단순하다. Terraform을 거쳐간 값은 state 파일에 평문으로 남는다. `SecureString` 타입이어도
state에는 그대로 적힌다. state 파일을 실수로 커밋하면 그게 곧 키 유출이다.

## 11. 토큰을 localStorage 대신 sessionStorage에 저장

둘 다 XSS에 취약하다는 점은 같다. sessionStorage는 탭을 닫으면 사라지므로 노출 창이
조금 짧을 뿐이다.

**제대로 하는 방법**: `HttpOnly` + `Secure` + `SameSite=Strict` 쿠키에 담아서 자바스크립트가
아예 접근하지 못하게 하는 것. 이 프로젝트에서는 CSRF 대응이 추가로 필요해져서 넣지 않았다.
실제 서비스라면 해야 한다.

## 운영 비용

서울 리전(ap-northeast-2) 기준 대략적인 월 비용. 정확한 금액은 AWS Pricing Calculator에서
직접 확인할 것.

| 항목 | 프리티어 (가입 12개월 내) | 이후 |
|---|---|---|
| t3.micro | 월 750시간 무료 | 약 $9 |
| EBS gp3 20GB | 30GB까지 무료 | 약 $2 |
| 퍼블릭 IPv4 주소 1개 | **무료 아님** | 약 $3.6 |
| ECR 스토리지 | 500MB 무료 | $0.10/GB |
| SSM Parameter Store (Standard) | 무료 | 무료 |
| 아웃바운드 트래픽 | 월 100GB 무료 | 이후 종량 |
| OpenAI API | — | 사용량만큼 |

프리티어 안에서도 **퍼블릭 IPv4 요금은 나간다**. 2024년 2월부터 연결 여부와 무관하게
모든 퍼블릭 IPv4에 과금된다. 안 쓰는 EIP를 방치하면 아무것도 안 하면서 돈이 새는 대표적인 경우다.

비용을 줄이려고 넣은 것들:

- ECR 라이프사이클 정책 — 최근 이미지 10개만 남기고 삭제
- Docker 로그 로테이션 (10MB × 3) — 디스크가 로그로 차면 EBS를 키워야 한다
- Redis `maxmemory` 상한
- `docker image prune` — 배포 성공 시마다 이전 레이어 정리

**반드시 할 것**: AWS Budgets에서 월 $5 정도로 알림을 걸어둘 것. 요금은 청구서를 볼 때가
아니라 새는 중에 알아야 한다.
